# 01a · 동시에 들어온 이벤트가 사라지는 결함

- 브랜치: `fix/01a-event-db-concurrency`
- 근거: [근거 문서](../plan/spec.md) R5(실시간 연동) · 01 실검증에서 찾은 기존 결함

## 목표

터미널 두 개를 함께 쓰거나 에이전트가 도구를 한꺼번에 여러 번 부를 때도 훅 이벤트가 하나도 빠지지 않고, 같은 세션의 이벤트는 들어온 순서대로 반영된다.

## 원인

- 이벤트 API 는 이벤트마다 백그라운드 작업으로 처리하므로 여러 이벤트가 동시에 DB 에 쓴다.
- 그런데 DB 엔진이 연결 하나(`StaticPool`)를 모든 세션이 같이 쓰게 돼 있었다. 그래서 한 작업의 커밋 · 롤백이 다른 작업의 반쯤 쓴 행에 섞였다. 로그에는 `StaleDataError` · `NoResultFound` 가 남고 세션 · 이벤트가 사라졌다.
- 같은 세션 안에서도 순서가 보장되지 않았다. 프롬프트가 자기 `session_start` 보다 먼저 처리되면 "복구용 시작" 이벤트가 하나 더 생겼다.

## 한 일

- `backend/app/db/database.py` — 엔진 생성을 `create_engine_for()` 로 뺐다. 파일 DB 는 세션마다 새 연결(`NullPool`)을 쓰고, WAL + `busy_timeout` 이 쓰기를 줄 세운다. 풀이 없으니 원본이 `StaticPool` 로 바꾼 이유였던 연결 풀 고갈도 생기지 않는다. 메모리 DB 는 연결이 하나뿐이라 `StaticPool` 을 그대로 쓴다.
- `backend/app/core/event_processor.py` — 세션마다 잠금을 하나씩 두고 이벤트를 들어온 순서대로 처리한다. 잠금은 약한 참조라 쓰는 작업이 없으면 사라진다.
- `backend/tests/test_event_db_concurrency.py` — 실제 파일 DB 로 3건: 세션 6개 동시 시작 · 한 세션의 `Read` 8번 동시 · 시작과 프롬프트가 겹칠 때 순서.

## 검증

| 단계 | 명령 · 방법 | 결과 |
| --- | --- | --- |
| 수정 전 재현 | 새 테스트를 원래 `StaticPool` 로 실행 | 3번 모두 실패 — 이벤트 12개 중 7개, 9개 중 4개만 저장 |
| 순서 테스트 되돌려 보기 | 세션 잠금만 빼고 실행 | 3번 모두 실패 (`session_start` 가 2개) |
| 정적 검증 | `make checkall` | 통과 — 백엔드 421(새 3) · 프런트 166 · 훅 24 · 플러그인 33 |
| 부하 | 세션 8개 × 이벤트 168개를 동시에 처리 (임시 스크립트) | 3번 모두 168/168 저장, 잠금 오류 0, 약 2초 |
| 지연 | 이벤트 60개를 하나씩 처리 | 1.2ms → 3.1ms. 화면 반영에 드러나지 않는 차이 |
| 실검증 | 빈 DB 백엔드에 세션 A · B 의 시작 · 프롬프트와 A 의 `Read` 8번을 간격 없이 POST, 3회 | 3회 모두 오류 0, 세션 2개, A: 시작 1 · 프롬프트 1 · 읽기 8 / B: 시작 1 · 프롬프트 1 |
| 스모크 회귀 | 서브에이전트 7명 시나리오를 사무실 화면으로 확인 | 줄 서기 · 자리 배정 정상, 콘솔 오류 0, 이벤트 23개 전부 저장 |
